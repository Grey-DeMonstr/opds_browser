# Android Release Pipeline — Design

Date: 2026-08-22

## Goal

Ship signed OPDS Browser releases from GitHub Actions to two channels:

- **GitHub Releases** — a universal APK for sideloading.
- **Google Play** — an AAB on the internal testing track.

A release is cut by pushing a `vX.Y.Z` tag. Everything after that is automated,
except the manual steps Play does not expose through its API.

## Decisions

| Question | Decision |
|----------|----------|
| Version source of truth | `pubspec.yaml` `version:` field — no separate VERSION file |
| Build number | `git rev-list --count HEAD` (commit count on `master`) |
| Release trigger | Push of a `vX.Y.Z` tag |
| Play track | `internal`; promotion to closed/production is manual |
| App signing key | Google-generated (standard Play App Signing) |
| Cross-channel upgrades | **Deliberately unsupported** — see Consequences |
| Privacy policy hosting | `PRIVACY.md` in this repo, served from github.com |
| Store assets | Generated by script, committed under `design/play/` |

## Version Model

`pubspec.yaml` keeps `version: 0.1.0+1`. A human only ever edits the `0.1.0`;
the `+1` exists so local `flutter build` keeps working.

CI computes the build number and overrides it:

```
flutter build appbundle --release --build-number=$(git rev-list --count HEAD)
```

This yields `versionName = 0.1.0` and `versionCode = 206` (at time of writing).

**Why commit count over alternatives:**

- `github.run_number` is not reproducible locally and silently resets to 1 if the
  workflow file is renamed or recreated, which would break `versionCode`
  monotonicity and permanently wedge Play upgrades.
- A dedicated VERSION file duplicates what `pubspec.yaml` already holds and adds
  a parser to keep in sync.

**Sharp edge:** `actions/checkout` defaults to a shallow clone, where
`git rev-list --count HEAD` returns `1`. The workflow MUST set `fetch-depth: 0`.

**Sharp edge:** every `versionCode` uploaded to Play is burned permanently and
can never be reused, including by discarded or failed releases.

### Tag/pubspec consistency guard

`tool/check_version.dart` is a thin CLI wrapper — it reads `pubspec.yaml` and
takes the tag as `args[0]` — around a pure function
`resolveVersion(String tagName, String pubspecContents)` that returns either the
agreed version or a descriptive error. All logic lives in the pure function; the
wrapper only does I/O and sets the exit code. The workflow calls it first and
fails fast when `v0.1.0` does not match `pubspec.yaml`.

This is the only real logic in the feature, so it is developed test-first with
unit tests in `test/tool/check_version_test.dart`. Cases: exact match; mismatched
version; tag missing the `v` prefix; malformed tag; pubspec with and without a
`+build` suffix; missing `version:` key.

Note this adds a `test/tool/` directory, which the layout in `CLAUDE.md` does not
currently list. `CLAUDE.md` is updated accordingly.

## Signing

A single upload keystore, generated locally, **never committed**.

`android/app/build.gradle.kts` reads `android/key.properties` when present and
falls back to the debug signing config when absent, so local
`flutter run --release` keeps working on a machine without the keystore.

```kotlin
val keystoreProperties = Properties()
val keystorePropertiesFile = rootProject.file("key.properties")
if (keystorePropertiesFile.exists()) {
    keystoreProperties.load(FileInputStream(keystorePropertiesFile))
}
// signingConfigs { create("release") { ... } }
// buildTypes { release { signingConfig = if (keystorePropertiesFile.exists())
//     signingConfigs.getByName("release") else signingConfigs.getByName("debug") } }
```

CI decodes `ANDROID_KEYSTORE_BASE64` into a file and writes `key.properties`
from secrets before building.

`.gitignore` gains `android/key.properties` and `**/*.jks`.

## Workflows

### `.github/workflows/ci.yml`

Triggers on push to `master` and on pull requests.

1. `actions/checkout`
2. `actions/setup-java` — Temurin **21** (Gradle 9.1.0 + AGP 9.0.1 require it,
   independent of the source/target compatibility 17 in `build.gradle.kts`)
3. `subosito/flutter-action` pinned to `3.44.1` stable, matching the dev machine
4. `flutter pub get`
5. `dart format --output=none --set-exit-if-changed .`
6. `dart run tool/check.dart` (analyze + test)

This does not exist today — nothing currently verifies pushes.

### `.github/workflows/release.yml`

Triggers on `push: tags: ['v*']`. Needs `permissions: contents: write`.

1. `actions/checkout` with **`fetch-depth: 0`**
2. Java 21 + Flutter 3.44.1, same as CI
3. `dart run tool/check_version.dart <tag>` — fail fast
4. `dart run tool/check.dart` — never release a red build
5. Decode keystore, write `key.properties`
6. `flutter build appbundle --release --build-number=$BUILD_NUMBER`
7. `flutter build apk --release --build-number=$BUILD_NUMBER`
8. Create the GitHub Release, attaching the APK renamed from Flutter's default
   `app-release.apk` to `opds-browser-<version>.apk`, with notes generated from
   the commit range since the previous tag (the repo uses conventional commits).
   For the first release there is no previous tag, so the range falls back to the
   full history.
9. Upload the AAB to Play, internal track

Two `flutter build` invocations roughly 1.5–2x the build time versus one. The
alternative — extracting a universal APK from the AAB with `bundletool` — needs
its own re-signing step and is not worth the complexity here.

Step 9 is added but left disabled until the first manual Play upload completes
(see Manual Prerequisites).

## Play Publishing

`r0adkll/upload-google-play`, **pinned to a commit SHA rather than a tag** — it
receives the service account JSON, and an unpinned third-party action is a
supply-chain hole. The rule is broader than this one action: any third-party
action running in a job that handles secrets is pinned to a commit SHA, which
is also why `subosito/flutter-action` is pinned in both workflows.

Service account setup (manual, one time):

1. Google Cloud project → create service account → enable the Google Play
   Android Developer API
2. Play Console → Users & permissions → invite the service account email
3. Grant release access to testing tracks for this app
4. Download the JSON key into the `PLAY_SERVICE_ACCOUNT_JSON` secret

Permission propagation is not instant; allow for a delay before the first
automated upload succeeds.

The action uploads binaries only. It does **not** manage store listing text or
graphics — that would require `fastlane supply` with metadata directories, which
is deliberately out of scope.

## Privacy Policy

`PRIVACY.md` at the repo root, referenced from the Play listing as
`https://github.com/Grey-DeMonstr/opds_browser/blob/master/PRIVACY.md`.
The repo is public, so the URL is reachable without login.

The policy is short because the app genuinely collects nothing. Verified against
the codebase:

- No authentication or credential handling anywhere in `lib/`.
- `shared_preferences` stores the chosen download-target folder (its SAF URI
  and display name) and two folder-layout booleans
  (`lib/data/shared_prefs_settings_repository.dart`); the catalogue's title
  and root URL are stored separately, in the local `sqflite` database
  (`lib/data/sqflite_catalog_repository.dart`).
- Book metadata also lives in that local `sqflite` database; downloads go to a
  user-chosen SAF folder.
- No analytics and no crash reporting.
- The only network traffic is to OPDS catalogue servers the user configures, and
  to whatever hosts those catalogues name for cover images.

This makes the Data Safety declaration "no data collected, no data shared".

**Standing risk:** Play requires this URL to remain live and login-free. Making
the repository private would put the listing in violation.

## Store Assets

`flutter_launcher_icons` and the Dart `image` package are unusable in this
project — `image` requires `xml ^6` / `archive ^4` against this project's
`xml ^7` / `archive ^3`. `tool/generate_app_icons.ps1` documents this and works
around it with PowerShell + `System.Drawing`. Play asset generation follows the
same approach for the same reason.

`tool/generate_play_assets.ps1` reads `design/logo.png` and writes into
`design/play/`:

- `icon-512.png` — 512×512, composited **opaque** over the existing `#0B0806`
  brand background. Play applies its own mask and should not be handed alpha.
- `feature-graphic-1024x500.png` — logo plus an "OPDS Browser" wordmark on the
  same background.

Both are committed. They are store assets, not app assets: they are not bundled
into the AAB, and they are uploaded to the Console by hand.

The generated feature graphic will be functional rather than designed — a flat
background, the logo, and text. It is adequate to pass review and ship, and is
expected to be replaced by hand later, like the screenshots.

Screenshots are explicitly **not** generated. The user will produce them.

## In-App Version Display

Add `package_info_plus` and show `version (build)` in
`lib/ui/settings_screen.dart`. For a sideloaded app this is what makes bug
reports actionable, and it is cheap to add while versioning is already being
touched. Widget test asserts the string renders from a fake.

## Testing Strategy

Per project constraints, everything runs on the host under `flutter test`.

- `test/tool/check_version_test.dart` — the tag/pubspec guard, test-first.
- Settings screen widget test for the version row, using an overridden provider
  so no platform channel is involved.
- The workflows themselves are not unit tested; they are validated by their
  first real run. The first release is therefore cut deliberately and watched.

## Repository Secrets

| Secret | Purpose |
|--------|---------|
| `ANDROID_KEYSTORE_BASE64` | Upload keystore, base64 encoded |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
| `ANDROID_KEY_ALIAS` | Key alias |
| `ANDROID_KEY_PASSWORD` | Key password |
| `PLAY_SERVICE_ACCOUNT_JSON` | Play Publishing API credentials |

`GITHUB_TOKEN` is provided automatically.

## Manual Prerequisites (cannot be automated)

Play will not publish until these are done by hand in the Console:

1. Enrol in Play App Signing with a Google-generated key (Setup → App integrity),
   **before** the first upload.
2. Upload the first AAB manually — the Publishing API cannot create the app or
   perform its first upload.
3. Privacy policy URL in the store listing.
4. Data Safety form.
5. Content rating questionnaire.
6. Target audience declaration.
7. Store listing: title, short and full description, `icon-512.png`,
   `feature-graphic-1024x500.png`, and at least two phone screenshots.
The developer account predates Nov 2023, so the 12-testers-for-14-days closed
testing requirement does not apply and production access is available
immediately. The internal track is still the CI target by choice, not by
constraint: it publishes instantly with no review wait, and it keeps the
decision to expose a build to real users a deliberate, human one made in the
Console.

## Consequences

**Cross-channel upgrades are unsupported, by decision.** With a Google-generated
app signing key, Play re-signs the AAB with a key we do not hold, while the
GitHub Releases APK carries the upload key's signature. Android will refuse to
install one over the other. A user switching channels must uninstall first and
will lose local data. This is documented in `README.md`.

`CLAUDE.md` currently states the repository is local only with no pushes needed.
That is stale — `origin` exists and `master` is pushed — and is corrected as part
of this work.

## Out of Scope

- `fastlane` for any purpose.
- Automated store listing text or graphics upload.
- Automated promotion between Play tracks.
- Split-per-ABI APKs. A universal APK keeps `versionCode` handling simple; app
  size is not currently a concern.
- Code shrinking / ProGuard / R8 tuning.
- iOS and Windows release automation. Android only, per project constraints.
- Automated screenshot generation.

## Implementation Order

1. `PRIVACY.md`
2. `tool/check_version.dart` + tests (test-first)
3. Signing config in `build.gradle.kts` + `.gitignore` updates
4. `.github/workflows/ci.yml`
5. `.github/workflows/release.yml`, Play step disabled
6. `tool/generate_play_assets.ps1` + committed `design/play/` output
7. `package_info_plus` version row in settings
8. `README.md` channel-incompatibility note, `CLAUDE.md` correction
9. Manual: keystore, secrets, Play Console setup, first upload
10. Enable the Play step; cut `v0.1.0`
